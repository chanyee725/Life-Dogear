# 제안서 — Research Brain을 "세컨드 브레인"으로 (PARA + 목표)

> 상태: **결정 반영 (2026-11-02)** — 8절 Q1~Q11 사용자 결정 완료. 디스코드 알림(10절)은 설계만, 구현 전 사용자 보고용 · 디자인 PM
> 사용자 요청 원문: "체계적으로, PARA 방식으로, 내 목표까지 여기서 다 정할 수 있는, 진짜 내 세컨드 브레인."
> 근거: `docs/SPEC.md`, `develop`의 `docs/PLAN.md`, `src/db/schema.ts`, `src/lib/enums.ts`, `src/components/shell/Sidebar.tsx` (develop `6fdd2bb` 기준)

## 0. 한 줄 요약

지금 만드는 1단계 MVP(연구·논문·세미나·생각 + 연결)를 **그대로 두고**, 그 위에 **영역(Area)·목표(Goal) 두 테이블과 `archived_at`(보관) 상태, 주간 검토 화면**을 얹는다.
새 "할 일 관리 앱"을 만드는 게 아니라, **매일 쓰는 흐름(빠른 입력 → 수집함 → 프로젝트/영역에 붙이기)과 주 1회 검토**만 추가한다.

## 1. 원칙

1. **1단계를 멈추지 않는다.** 기존 테이블·경로·컴포넌트는 이름과 동작을 유지한다. 변경은 컬럼 추가와 새 테이블뿐 (테이블 재작성·파괴적 마이그레이션 없음).
2. **기존 `links`·`item_tags` 재사용.** 새 관계는 가능한 한 기존 다대다 연결로 표현하고, "소속"(한 프로젝트는 한 영역에 속함)처럼 계층이 필요한 곳에만 컬럼을 쓴다.
3. **보관함은 테이블이 아니라 상태.** 모든 항목에 `archived_at` 하나.
4. **매일 쓰는 것만.** 할 일 목록·반복 일정·습관 트래커는 만들지 않는다. 프로젝트마다 "다음 할 일" 한 줄이 전부. 알림은 **주 1회 디스코드 주간 검토 알림 하나**뿐(10절).
5. **디자인 톤 유지.** 조용하고 미니멀(Linear/Things/Craft/Reflect). 새 화면도 무채색 + 포인트 색 1개, 얇은 구분선, 8px 모서리, 은은한 배지. 진행률 바만 포인트 색을 쓴다.

## 2. PARA 매핑

| PARA | 이 앱에서 | 저장 방식 | 비고 |
|---|---|---|---|
| **Projects** (마감·끝이 있는 일) | **프로젝트** = 지금의 "연구" + 연구 외 프로젝트 | 기존 `projects` 테이블 + `kind`(`research`/`general`) | 연구는 기존 8단계 그대로. 일반 프로젝트는 단계 없이 상태만 |
| **Areas** (계속 책임지는 영역) | **영역** — 예: 연구 분야, 학위, 건강, 커리어 | 새 `areas` 테이블 | 영역은 끝나지 않는다. "유지 기준" 한 줄을 가진다 |
| **Resources** (관심 주제별 자료) | **자료** = 논문 · 세미나 · 정리된 생각, **주제 = 태그** | 기존 `papers`·`seminars`·`thoughts` + `tags` | 새 테이블 없음. 사이드바 "태그"를 "주제"로 부른다(결정 Q4) |
| **Archives** (끝났거나 비활성) | **보관함** | 모든 타입에 `archived_at` 컬럼 | 목록에서 기본 숨김, 보관함 화면에서 한꺼번에 보고 되살리기 |
| (PARA 밖) **Goals** | **목표** — 연·분기 | 새 `goals` 테이블 | 영역에 속하고, 프로젝트가 목표를 향한다 |

### 2.1 관계 한눈에

```
 영역(Area) ──< 목표(Goal: 연) ──< 목표(Goal: 분기)
    │                                   │
    └──────────< 프로젝트(Project) >─────┘        ← area_id, goal_id (소속, 0~1개)
                     │
                     └── links ── 논문 · 세미나 · 생각 · 다른 프로젝트 · 영역  (다대다, 기존 그대로)
```

- **소속(계층)** 은 컬럼: `projects.area_id`, `projects.goal_id`, `goals.area_id`, `goals.parent_id`. 사이드바 묶음·진행률 계산처럼 "하나의 부모"가 필요한 곳만.
- **참조(그물)** 는 기존 `links`: 논문↔영역, 생각↔목표 등 무엇이든. `ITEM_TYPE`에 `area`, `goal`만 추가하면 연결 피커·연결된 항목 UI를 그대로 쓴다.

### 2.2 생각(Thought)은 어디에?

생각은 PARA 칸이 아니라 **흐름**이다. 위치는 연결로 정해진다.

| 생각의 상태 | 보이는 곳 |
|---|---|
| 연결도 태그도 없음 (빠른 입력으로 막 들어옴) | **수집함** (홈 숫자 + `/inbox`) |
| 프로젝트·영역·목표에 연결됨 | 그 프로젝트/영역/목표 상세의 "생각" 묶음 |
| 태그(주제)만 있음 | **자료**의 해당 주제 아래 |
| `archived_at` 있음 | 보관함 |

→ **수집함 = "연결 0개 + 태그 0개 + 보관 안 됨"인 생각**. 새 컬럼 없이 계산한다. "정리한다"는 것은 연결하거나, 주제를 달거나, 보관하는 것 셋 중 하나.

## 3. 목표(Goal)와 루틴

### 3.1 목표 구조 (최소)

- 기간: **연 목표**(`2027`)와 **분기 목표**(`2027-Q1`) 두 단. 분기 목표는 연 목표 하나에 속할 수 있다(`parent_id`).
- 각 목표: 제목, 왜 중요한가 한 줄, 영역(선택), 상태(`active` 진행 중 · `achieved` 달성 · `dropped` 내려놓음), 본문.
- 프로젝트는 `goal_id`로 목표 하나를 향한다 (보통 분기 목표).

### 3.2 진행률 보는 법

| 방식 | 계산 | 언제 |
|---|---|---|
| **자동 (기본)** | 이 목표를 향한 프로젝트 중 `done` 비율. 연 목표는 하위 분기 목표들의 평균 | 프로젝트가 1개 이상 연결된 경우 |
| **수동** | 0–100 슬라이더 (10 단위) | 프로젝트로 재기 어려운 목표(예: "주 3회 운동") — 주간 검토에서 갱신 |

표시: 제목 옆 얇은 4px 바(포인트 색) + 숫자 `60%`. 주간 검토 때 남긴 값이 쌓이므로 "지난주 대비 +10%"만 작게 보여준다. 차트는 만들지 않는다.

### 3.3 주간 검토 (Weekly Review) — 10분짜리 4단계

`/review` 한 화면에서 위→아래로 진행. 각 단계는 접히는 섹션이고 끝나면 체크 표시.

1. **수집함 비우기** — 수집함의 생각마다: 프로젝트/영역에 연결 · 주제 달기 · 보관 (한 줄에 버튼 3개, 키보드 `1` `2` `3`).
2. **프로젝트 점검** — 진행 중 프로젝트 목록. 각 줄: "다음 할 일" 한 줄 수정, 상태 바꾸기(진행 중/보류/완료). 14일 이상 손대지 않은 프로젝트는 회색 점으로 표시. 완료된 프로젝트는 "보관할까요?" 제안.
3. **목표 점검** — 이번 분기 목표별 진행률 확인, 수동 목표는 슬라이더로 갱신, 한 줄 메모.
4. **다음 주 집중 3가지** — 프로젝트·목표 중 최대 3개 선택 → 홈 상단 "이번 주 집중"에 표시. 마지막에 자유 회고 메모(마크다운, 양식: 잘 된 것 / 막힌 것 / 다음 주).

"검토 완료"를 누르면 그 주(`2026-W45`) 기록이 저장된다. 지난 검토는 `/review/2026-W44`처럼 읽기 전용으로 볼 수 있다.
알림은 **디스코드 메시지 주 1회**뿐(결정 Q10, 설계는 10절): "주간 검토할 때예요" 문구와 앱 링크만 보낸다. 앱 안에는 따로 알림 줄·배지·점을 두지 않는다. 지난 검토 날짜는 `/review` 화면 아래 "지난 검토" 목록에서만 보인다.

### 3.4 매일 흐름 (새로 배울 것 없음)

```
떠오름 → 홈 빠른 입력(/) → 수집함 ─┬→ 프로젝트·영역에 연결   (상세 화면 "연결된 항목", 기존 UI)
                                  ├→ 주제(태그) 달기       (기존 TagInput)
                                  └→ 보관
논문 읽기 → 이어 읽기 → 생각 만들기 → (논문과 자동 연결되므로 수집함에 안 들어감)
```

### 6.2 마이그레이션 영향

- `drizzle-kit generate`로 `0001_*.sql` 한 개: `ALTER TABLE … ADD COLUMN` × 9 + `CREATE TABLE` × 3 + 백필 `UPDATE` 1문. SQLite `ADD COLUMN`은 테이블 재작성 없이 동작하고 Turso(libSQL)에서도 같다.
- 확인함: 현재 `0000` 마이그레이션은 enum 컬럼에 `CHECK` 제약을 만들지 않는다 → `ITEM_TYPE`에 `area`·`goal`을 추가해도 `links`·`item_tags`는 SQL 변경 불필요.
- 단, `ADD COLUMN`으로 추가하는 FK(`area_id`, `goal_id`)는 SQLite 제약상 기본값이 NULL이어야 한다 — 위 표대로 null이라 문제 없음. drizzle-kit이 테이블 재작성(`__new_projects`)을 생성하면 손으로 `ADD COLUMN`으로 바꾸고 리뷰 받는다.
- 코드 영향(구현 시): `src/lib/repo/items.ts`의 `TABLES` 맵·`searchTitles`에 `areas`·`goals` 추가, 목록 repo의 `list()`에 `archived` 필터 기본값 추가, 삭제 트랜잭션에 새 타입 포함.

### 6.3 기존 데이터 이전

1. 마이그레이션이 자동으로: 기존 연구 → `kind=research`, 제출 완료 → `status=done`. 데이터 손실 없음, 되돌리기는 새 컬럼 무시로 충분.
2. **첫 실행 안내** (영역이 0개일 때 사이드바 "영역" 아래 한 줄): "영역을 만들어 프로젝트를 묶어 보세요" → 추천 4개(연구 분야·학위·건강·커리어) 체크박스로 한 번에 생성. 자동 생성은 하지 않는다.
3. 기존 프로젝트의 영역 지정은 첫 주간 검토 2단계에서 줄마다 `영역 ▾`로 처리.
4. seed(`npm run db:seed`) 갱신: 가짜 영역 4, 목표 3(연 2·분기 1), 일반 프로젝트 1, 보관된 항목 1, 지난 검토 1. 인물명 가짜, 이메일 없음.

## 10. 디스코드 알림 설계 (구현 전 사용자 보고용)

> 결정 Q10에 따른 설계안이다. **구현하지 않았다.** 아래 권장안과 10.10의 질문에 사용자가 답한 뒤 2단계(주간 검토와 함께)에 만든다.
> 디스코드는 외부 서비스다. 보낸 메시지는 디스코드 서버에 저장되고, 휴대폰 알림 미리보기(잠금 화면)에도 보인다. 그래서 메시지에 담는 내용을 최소한으로 고정한다.

### 10.1 조건 (고정)

- **메시지 내용**: "주간 검토할 때예요" 수준의 고정 문구 + 앱 링크만. 항목 제목·메모·태그·목표명·프로젝트명·수집함 개수 등 **앱 데이터는 한 글자도 넣지 않는다.**
- **비밀값**: 웹후크 URL(또는 봇 토큰)은 사용자가 `.env`에 직접 넣는다. 세션·코드는 `.env`를 읽거나 만들지 않고 `.env.example`에 **빈 키만** 둔다.
  ```
  # 디스코드 주간 검토 알림 (비워 두면 알림을 보내지 않음)
  DISCORD_WEBHOOK_URL=
  # 알림 메시지의 앱 링크 주소 (기본 http://127.0.0.1:3000)
  APP_BASE_URL=
  ```
- 비밀값은 로그·에러 메시지·커밋 어디에도 남기지 않는다. 로그에는 HTTP 상태 코드와 "보냄/건너뜀/실패"만 남긴다.
- 키가 비어 있으면 아무것도 보내지 않고 조용히 끝난다(오류 아님).

메시지 예시(이게 전부다):

```
Research Brain
주간 검토할 때예요.
이 컴퓨터에서 열기 → http://127.0.0.1:3000/review
(앱이 켜져 있을 때 열립니다)
```

- `allowed_mentions: { parse: [] }`로 `@everyone` 같은 멘션이 절대 생기지 않게 하고, 임베드·미리보기 카드는 쓰지 않는다.

### 10.2 언제 보내나 (판단 규칙)

1. 정해진 시각(기본 **일요일 20:00, 이 컴퓨터의 현지 시간**)에 판단 스크립트가 실행된다.
2. 이번 주(ISO 주, 예 `2026-W45`)의 `reviews` 행 중 `completed_at`이 있는 행이 있으면 → 보내지 않는다.
3. `app_state.weekly_notice_week`가 이미 이번 주면 → 보내지 않는다(중복 방지, 10.4).
4. 그 외에는 1통 보낸다. **한 주에 최대 1통**, 재알림 없음.

### 10.3 실행 방식 비교

| | (a) 앱 내부 스케줄러 | (b) 별도 cron 스크립트 (권장) |
|---|---|---|
| 구조 | Next 서버가 시작될 때(`instrumentation.ts`) 타이머를 등록해 주기적으로 판단 | `npm run notify:weekly` 한 번 실행 = 판단 + 전송 후 종료. OS 스케줄러가 주 1회 실행 (Linux: systemd user timer, macOS: launchd, 또는 crontab) |
| 앱이 꺼져 있을 때 | **보내지 못함**. 개인용 로컬 앱이라 일요일 저녁에 꺼져 있을 가능성이 큼 | 보냄. DB만 읽어 판단하므로 앱 서버는 필요 없음 |
| 컴퓨터가 꺼져/잠들어 있을 때 | 보내지 못함 | systemd `Persistent=true`·launchd는 다음에 켜질 때 한 번 실행 → 늦게라도 1통 |
| 중복 위험 | dev 서버 재시작·HMR·여러 프로세스로 타이머가 겹칠 수 있어 DB 잠금이 꼭 필요 | 실행이 주 1회뿐이라 낮음. 그래도 10.4의 DB 기록으로 막음 |
| 설치 부담 | 없음 | OS 스케줄러를 한 번 등록해야 함 → 예시 파일(`ops/notify-weekly.timer` 등)과 README 안내 제공. **등록은 사용자가 직접** |
| 테스트 | 시간 흐름을 흉내 내기 어려움 | `npm run notify:weekly -- --dry-run`으로 "보낼지/왜"만 출력, `--now 2026-11-08T20:00` 같은 시각 지정으로 단위 테스트 쉬움 |
| 앱 코드 영향 | 서버 시작 경로에 백그라운드 작업이 생김 | `scripts/`에 독립 스크립트 1개. 앱 실행 경로는 그대로 |

**권장: (b) 별도 cron 스크립트.** 세컨드 브레인 알림의 목적은 "앱을 안 열었을 때 열게 만드는 것"인데, (a)는 앱이 켜져 있을 때만 동작해서 목적과 맞지 않는다.

### 10.4 중복 전송 방지

- 마지막 전송 기록은 **DB의 `app_state` 테이블**에 둔다(`key='weekly_notice_week'`, `value='2026-W45'`, `updated_at`). 파일(`data/`)이 아니라 DB에 두는 이유: Turso를 쓰면 여러 기기에서 스크립트가 돌아도 같은 기록을 보기 때문이다.
- 순서는 **"먼저 선점 → 전송 → 실패하면 선점 취소"**:
  1. `UPDATE app_state SET value=:week … WHERE key='weekly_notice_week' AND value IS NOT :week` (행이 없으면 INSERT … ON CONFLICT DO NOTHING). 바뀐 행이 0이면 다른 실행이 이미 보낸 것이므로 끝낸다.
  2. 디스코드로 전송.
  3. 전송이 최종 실패하면 값을 이전 주로 되돌려 다음 실행이 다시 시도하게 한다.
- 이렇게 하면 두 실행이 동시에 돌아도 1통만 나간다. 선점 후 프로세스가 죽는 드문 경우에는 그 주 알림이 빠질 수 있다. 알림이 두 번 가는 것보다 낫다고 판단했다.

### 10.5 실패 처리

| 상황 | 처리 |
|---|---|
| 키 비어 있음 | 전송 안 함, 종료 코드 0 ("알림 설정 안 됨" 한 줄) |
| 네트워크 오류·타임아웃(10초)·5xx | 1회 재시도(수 초 대기) → 그래도 실패면 선점 취소, 종료 코드 1 (systemd/launchd 로그에 실패로 남음) |
| 429 (요청 제한) | 응답의 `retry_after`만큼 기다려 1회 재시도. 주 1통이라 실제로는 거의 없음 |
| 401/403/404 (웹후크 삭제·토큰 무효) | 재시도 안 함, 선점 취소, 종료 코드 1, 로그에 "웹후크 주소를 확인하세요"와 상태 코드만 |
| DB 접속 실패 (Turso 오프라인 등) | 판단 불가 → 보내지 않음, 종료 코드 1. 다음 예약 실행 때 다시 판단 |

다음 주까지 계속 실패하면 그냥 그 주 알림은 빠진다. 별도 재시도 큐는 만들지 않는다.

### 10.6 DB별 동작 (로컬 파일 / Turso)

- 스크립트는 앱과 **같은 설정 로더**(`src/db/config.ts`의 `resolveDbConfig`, `loadEnvIfPresent`)를 쓴다. 따라서 `.env`의 `DATABASE_URL` 유무로 로컬/Turso가 자동으로 정해진다. OS 스케줄러는 **저장소 폴더를 작업 폴더로** 실행해야 한다(`WorkingDirectory=`).
- **로컬 파일 DB** (`DATA_DIR/local.db`): 앱이 꺼져 있어도 파일만 읽으면 된다. 그 컴퓨터가 켜져 있어야 하고, 쓰기는 `app_state` 한 행뿐이라 앱과 동시에 실행돼도 문제없다.
- **Turso**: 네트워크가 필요하다. 오프라인이면 10.5대로 건너뛴다. 여러 기기에 타이머를 등록해도 10.4 덕분에 1통만 나간다. **권장은 기기 하나에만 등록**하는 것이다.
- GitHub Actions 같은 원격 실행은 DB 토큰을 외부 CI에 맡겨야 해서 이번 제안에서 뺀다(CI·인프라 변경은 별도 승인 사항).

### 10.7 링크 주소 (127.0.0.1 문제)

- 앱은 `127.0.0.1`에만 열려 있다(`next dev -H 127.0.0.1`). 그래서 링크 `http://127.0.0.1:3000/review`는 **앱을 켠 그 컴퓨터에서만** 열린다. 휴대폰 디스코드에서 누르면 열리지 않는다.
- 문구 처리: 링크 앞에 "이 컴퓨터에서 열기", 뒤에 "(앱이 켜져 있을 때 열립니다)"를 붙여 기대를 맞춘다. 휴대폰에서는 "검토할 때"라는 신호로만 쓴다.
- 포트·주소가 다르면 `APP_BASE_URL`로 바꾼다. 앱을 외부(LAN·터널)에 여는 것은 보안상 권하지 않으며 이 제안 범위 밖이다.

### 10.8 웹후크 vs 봇 토큰

| | 디스코드 **웹후크** (권장) | 디스코드 **봇 토큰** |
|---|---|---|
| 준비 | 내 서버의 비공개 채널 → 채널 설정 → 연동 → 웹후크 만들기 → URL 복사 | 개발자 포털에서 앱·봇 생성 → 토큰 발급 → 내 서버에 초대하거나 DM 경로 준비 |
| 보내는 곳 | 그 채널 하나 | 채널 또는 내 DM. 단 DM은 보통 봇과 같은 서버에 있어야 하며, 구현 전 확인 필요 |
| 비밀값이 새면 | 그 채널에 글을 쓸 수 있음(읽기 불가). 웹후크 삭제로 즉시 무효화 | 봇이 들어간 모든 서버에서 봇 권한만큼 행동 가능 → **피해 범위가 더 큼** |
| 구현 | HTTPS POST 한 번, 라이브러리 불필요 | REST 호출 2단계(DM 채널 열기 → 메시지) + 봇 계정 제약 확인 필요 |
| 앞으로의 확장 | 보내기만 가능 | 버튼·명령으로 "검토 완료" 같은 상호작용 가능. 단 디스코드가 앱으로 요청을 보내야 하는데, 127.0.0.1 앱은 외부에서 받을 수 없어 사실상 불가 |
| 겉모습 | 메시지 작성자 이름을 "Research Brain"으로 지정 가능(봇처럼 보임) | 봇 계정 이름으로 표시 |

**권장: 웹후크.** 사용자가 말한 "봇 알림"의 체감(정해진 이름으로 오는 자동 메시지)은 웹후크로도 똑같다. 필요한 비밀값이 더 작고, 새어도 피해가 그 채널 쓰기로 한정된다. DM으로 꼭 받아야 할 때만 봇 토큰을 쓴다.

### 10.9 개인정보 노출 범위

| 무엇이 | 어디로 | 내용 |
|---|---|---|
| 알림 메시지 | 디스코드 서버(저장), 휴대폰 푸시 경로(Apple/Google) | 고정 문구 + `127.0.0.1` 링크. 앱 데이터 없음. 드러나는 것은 "이 사람이 주간 검토 루틴을 쓴다"와 로컬 포트 번호 정도 |
| 웹후크 URL | 사용자 `.env`에만 | 코드·로그·커밋·`.env.example`에 없음 |
| DB 내용 | 이 컴퓨터(또는 이미 쓰는 Turso) | 스크립트가 `reviews` 완료 여부와 `app_state`만 읽고 씀. 외부로 보내지 않음 |

### 10.10 권장안 요약과 사용자에게 물을 것

**권장안**: (b) `npm run notify:weekly` 스크립트 + OS 타이머(이 Linux 기기는 systemd user timer, `Persistent=true`) + **디스코드 웹후크**(내 서버의 비공개 채널). 일요일 20:00에 그 주 검토가 끝나지 않았으면 고정 문구와 링크 1통을 보낸다. 중복 방지는 DB `app_state`에서 한다. 2단계(주간 검토)와 함께 만든다.

| # | 질문 | 선택지 (★ 권장) |
|---|---|---|
| D1 | 받는 방식 | ★ 웹후크 → 내 서버의 비공개 채널 · 봇 토큰 → 내 DM |
| D2 | 실행 방식 | ★ 별도 스크립트 + OS 타이머(앱 꺼져 있어도 동작) · 앱 내부 스케줄러(앱 켜져 있을 때만) |
| D3 | 보내는 시각 | ★ 일요일 20:00 · 다른 요일·시각 지정 · "마지막 검토 후 7일" 기준 |
| D4 | 앱을 켜는 컴퓨터 | 이 Linux 기기 하나인가요? (타이머 예시 파일을 어느 OS용으로 준비할지 결정) |
| D5 | 문구에 "지난 검토 N일 전"을 넣을까요? | ★ 넣지 않음(고정 문구만) · 넣음(숫자 하나만, 앱 데이터 최소 노출) |
| D6 | 재알림 | ★ 주 1통만 · 다음 날 한 번 더 |
